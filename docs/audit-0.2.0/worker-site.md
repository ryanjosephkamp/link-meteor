Initial static audit on `codex/audit-0.2.0` at `41f82e58066d57aa19c44b00dc8bb07c8cf81407` (September 25, 2026). Scope: `site/`, `.github/workflows/pages.yml`, `scripts/sync-site.mjs`, and extension source only to check site claims. The user chose to keep offering the development ZIP. ## Findings

1. **[P2] Manual deployment can publish a non-main ref.** `.github/workflows/pages.yml:6-7,18-36` allows `workflow_dispatch` and then publishes the checkout selected for that run. It has no `github.ref == 'refs/heads/main'` condition. `site/README.md` describes merging to `main` first, but that prose does not enforce the gate. A manual run selecting an audit or other feature branch would publish its `site/` and development ZIP. **Remedy:** constrain the deploy job to the intended reviewed ref (and use the protected `github-pages` environment if appropriate); verify the selected commit before a manual release. This is a static workflow inference; no action was dispatched.

2. **[P2] The deploy check does not establish that the ZIP represents current extension source.** `scripts/sync-site.mjs:12-20,29-35,47-64` compares selected source files with site copies, the artifact ZIP with the site ZIP, and generated metadata. It never checks whether `artifacts/link-meteor-0.2.0.zip` was built from current `src/background.js`, `src/content/capture.js`, `src/ui/workbench.js`, or other packaged files. `.github/workflows/pages.yml:29-34` treats this as the only build consistency gate before uploading the site. **Reproduction from control flow:** change an extension source file outside the seven sync pairs without rebuilding the artifact; all comparisons can still pass, so the site can offer an older build while describing newer behavior. **Remedy:** require reproducible package provenance or compare the ZIP's member hashes to current source at deploy time; alternatively generate the package from the checked-out commit and compare it with the offered ZIP. I did not mutate source to simulate this case.

3. **[P3] The install page understates the actual user test while naming the tested environment.** `site/install.html:66` says everyday Chrome installs have not been tested. `docs/ACCEPTANCE.md:26` records that the user loaded the 0.2.0 build unpacked in everyday Google Chrome and reported that it worked, with steps not itemized. The same acceptance document still labels specific everyday Chrome interactions unverified (`docs/ACCEPTANCE.md:28`). **Remedy:** update the install note to distinguish the user's broad report from the repeatable automated tests and the specific unverified cases. Do not turn the report into a claim that native prompts, all flows, or other platforms passed.

4. **[P3] The Excel preview's semantic table labels the data columns “A” and “B”.** In `site/assets/js/site.js:222-230`, the first row uses `<th>` for A/B, while the actual “Anchor text” and “URL” labels are `<td>` in the next row. The table semantics designate spreadsheet letters as headers, obscuring which data field each column contains for assistive navigation. The simpler selected-links table in `site/index.html:86-89` has correct `<th scope="col">` headers. **Remedy:** make Anchor text and URL the semantic column headers in the preview, with A/B and row numbers kept as visual decoration or otherwise marked so they do not replace data headers. Static DOM construction establishes this issue; no screen-reader session was run.
