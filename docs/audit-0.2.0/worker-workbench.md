I read `docs/CONTRACTS.md`, `docs/ACCEPTANCE.md`, `docs/alignment/2026-09-25/ALIGNMENT.md`, and `docs/opus-handoff/OPUS_RETURN.md`.

## Findings

1. **P2 — Remove acts on links hidden by the current view.** `renderLinks` retains selected IDs when filters or the batch view change (`workbench.js:230-247`), and `renderExportTarget` explicitly restricts exports to selected links *in this view* (`:529-568`). The Remove button remains enabled for any saved selection and sends *all* selected IDs to `links.remove` (`:943`). Reproduce: select a row, search for a different link (or choose a capture batch excluding it), then click Remove while the selected row is absent; the hidden link is removed. This is reversible through Undo, but the action's visible target and the export target disagree. Make Remove use selected IDs in the current view, or clearly show/confirm the count of hidden selected links before removal and offer a way to review them.

2. **P2 — Keyboard focus is discarded after checking an individual row or tab.** A row checkbox change calls `renderLinks`, which replaces `#link-list` (`workbench.js:363-366`, `:261-275`); focus restoration handles only note/tag inputs with `data-link-id`, not row checkboxes. Similarly, a tab checkbox change calls `renderInventory`, which replaces `#tab-options` (`:663-665`, `:656-657`). Reproduce with keyboard: focus an individual checkbox and press Space; its focused node is removed. Subsequent Space/Tab does not continue from that checkbox. Retain and restore focus by stable link/tab ID, or update checkbox state and counts without replacing the focused control. The same pattern existed in the baseline, so this is a retained acceptance gap rather than a new Opus regression.

3. **P2 — Capture-report batch action can point at the wrong collection.** `captureReport` creates `Show only these links` once if the batch is present in the then-active collection (`workbench.js:750-760`), while collection activation clears the batch filter but does not refresh or remove that report action (`:185-193`). Reproduce: capture into collection A, switch to collection B while the report stays visible, then click its batch action. `renderLinks` finds no matching links and clears the filter (`:222-224`), but the report button has already changed to `Show all links`. The action claims a filtered state that does not exist. Tie the report action to the collection ID and recompute its availability/label on activation and state reload.

4. **P3 — “Only the latest capture” can describe an older batch.** The new view chip uses a fixed label (`workbench.js:311`), while a new `capture.run` updates `flashBatch` and state without clearing or replacing `ui.batchFilter` (`:799-801`). Reproduce: filter to batch A through the report, capture batch B, and inspect the view chip: it still filters A but reads “Only the latest capture.” Clear the batch filter on a new capture, or label it with the captured batch/time and update the report action accordingly.

## Scope checks and limits

- The permission requests in `chooseScope` (`workbench.js:699-705`), `runCapture` (`:771-799`), `bookmark` (`:830-839`), and `configureHold` (`:871-882`) begin from their direct user handlers without a preceding asynchronous step. The code freezes selected tab IDs before origin requests and checks surviving tabs for origin drift. This is static call-order evidence only; automated grants in `ACCEPTANCE.md` do not establish native Allow/Deny prompt behavior.
- Inline Open computes unique HTTP(S) URLs and rejects more than 20 before displaying confirmation (`workbench.js:842-854`); `links.open` is called only from the confirmation handler (`:862-869`). Changes to the target URL set invalidate pending confirmation (`:585`). Static review found no cap bypass in this UI path.
- Draft maps retain unsaved collection and per-link input through ordinary re-renders; query grouping retains occurrence IDs; `targetRows` restricts export/bookmark/open to the matching selected occurrences, and export copy/download call the shared `makeExport`. I did not execute exports or browser UI in this worker pass.
- During the initial static pass, no product code, tests, build artifact, Git history, protected branch/tag/PR, or unpacked Chrome build was changed. Checks actually run then: read-only `git status`, `git rev-parse HEAD`, `git diff`/`git show` against the baseline, `rg`, and numbered source reads. Browser/native/assistive-technology behavior remains for Astra's independent checks and the user's unitemized everyday-Chrome report remains unitemized.

## Narrow repair after Astra accepted the findings

The audit driver assigned exclusive ownership of `src/ui/workbench.js` for these repairs. Remove now uses selected occurrence IDs in the current filtered/grouped view; it is disabled when that intersection is empty. It leaves hidden selections intact, while the reducer's existing positional Undo covers the removed IDs. The Select all N notice counts IDs in this view rather than all retained selections. Individual row checkbox, details summary, and tab checkbox focus is restored by stable row/tab identity after list re-render, preserving the existing note/tag draft restoration. The capture-report action is recomputed from the active collection and batch filter on each render; it disappears when the batch is absent and its label follows the current filter. The batch chip now reads “Selected capture,” so a later capture cannot make an older batch look latest.

Repair verification actually run: `node --check src/ui/workbench.js` passed; `git diff --check -- src/ui/workbench.js` passed; `npm test` passed 23/23. No browser, native prompt, clipboard, download, or assistive-technology test was run by this worker after repair. The driver owns loaded-extension regression checks and final acceptance labels.
