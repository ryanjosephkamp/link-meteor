# Capture/background static review — 2026-09-25

Scope: one read-only pass over `src/content/capture.js` and `src/background.js` against `docs/CONTRACTS.md` and `docs/IMPLEMENTATION.md`. No product edits, tests, or browser run were performed for this review.

## Actionable findings

1. **P1 — Revoking a site's persistent grant does not disable hold mode in saved settings or an already injected script.** `src/background.js:180-190` filters revoked origins only when registering future content scripts; `src/background.js:264` invokes that sync on permission removal. It does not remove the origin from `settings.holdOrigins` or send `content.configure` with `enabled:false` to open tabs. `src/content/capture.js:189-197` derives `holdEnabled` from that persisted list and only refreshes on storage changes or an explicit message. Thus an existing script can keep accepting the hold gesture after a grant is revoked if Chrome leaves it loaded. Even if Chrome discards it, a later explicit `capture.arm` injection on that origin (`src/background.js:81-84`) reads the still-enabled setting and activates the hold gesture without a persistent grant. `capture.commit` checks for a tab sender but not the current origin grant (`src/background.js:139-145`). Reconcile revoked origins in state and notify open content scripts; ensure hold activation requires a current grant. Chrome's exact behavior for a loaded content script on revocation still needs browser verification, but the persisted-setting/reinjection path follows directly from the code.

2. **P1 — The page context menu loses denial, unsupported-page, and partial-coverage reports.** `captureTabs` constructs per-tab statuses and warnings (`src/background.js:115-136`), but the `meteor-page` handler discards its returned report and opens the workbench unconditionally (`src/background.js:248-250`). A denied or unsupported page can therefore look like an unchanged or empty collection to that user path, contrary to the required visible failure and coverage reporting. Carry the report into the workbench (for example through a task-owned session record) or surface the non-success result before opening it. This is a definite control-flow defect; the exact visible workbench state was not browser-tested here.

3. **P2 — A session-target write failure can produce two contradictory results for one tab.** `captureTabs` persists links, increments `capturedCount`, and pushes a success result before awaiting `rememberTarget(tab)` (`src/background.js:125-130`). If that session write fails, the same `try` falls into the catch and appends an error result for the same tab (`src/background.js:131-134`). Keep target bookkeeping from changing capture status after a successful persistent write, and report a target warning separately if useful. This failure path follows directly from the code; its frequency in Chrome is unmeasured.

4. **P2 — Concurrent hold configuration can race in script registration.** State mutations are serialized (`src/background.js:9-12,28-35`), but `configureHold` calls `syncHoldScripts` afterward (`src/background.js:193-201`). Two workbench requests can both unregister/re-register the same `meteor-hold-sites` ID (`src/background.js:186-189`) with interleaved results, causing a duplicate-registration error or a final registration that does not reflect the last saved origins. Serialize the permission check and registration reconciliation as one operation, or make registration idempotent against the latest state. This is an interleaving supported by the code; no browser race reproduction was run.

## Limits of this pass

The regional code uses positive-area rectangle intersection and retains selected links while scrolling (`src/content/capture.js:33-43,133-158`). I did not run pointer drags, nested scrolling, wrapped-anchor, transformed-frame, clipboard, or native shortcut checks. Static inspection cannot establish those browser behaviors or human visual acceptance. I did not find a separate definite anchor-text substitution or state overwrite path in this pass.
